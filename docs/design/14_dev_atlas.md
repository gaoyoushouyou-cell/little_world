# 14 開発の地図帳（Dream Atlas）— 提案

> 状態：**P0 まで実装済み**（13 章、決定 75〜77）。11 章の論点はすべて合意済み（決定 69〜74）。P1 以降は合意を得てから始める。

マインドマップのアプリ（MindBloom、`python作品/1_mindmapapp`）を改造して、
little world の **世界のつながり・進行の依存関係・開発の進み具合** を、ひとつの絵の上で機械的に検査できる道具にする。

---

## 1. なぜ必要か（ゲームから見えた問題）

little world はメトロイドヴァニア型（決定 9・16）で、次のものが互いに依存している。

| 要素 | 依存のしかた | 壊れ方の例 |
|---|---|---|
| エリアのつながり | 端で隣り合う／ワープ（一方通行あり）／出入口 | 一方通行のワープの先から戻る道がない |
| 夢のかけら | `requires` でエフェクト・mood・フラグを要求 | 取るのに要るエフェクトが、そのかけらを使わないと解放できない（循環） |
| エフェクトの木 | 前提エフェクト＋かけらの数 | 世界中のかけらを集めても数が足りない |
| mood（20 通り） | 変える動作がある場所に依存。ベッドで白×風に戻る | 必要な mood を作る場所がどこにもない／作れる場所から目的地まで mood を保てない |
| 世界のフラグ | 遠いエリアの動作で立つ | 立てる場所がない（読むだけのフラグ） |
| 深さと沈み | 深さ 4 以上は重さ N が要る | 浅いエリアに重りの素材がない |
| エリア規則 | `effectPolicy` でエフェクトを封じる | 塔の中のかけらが、封じられた風船を前提にしている（C-11） |
| 拠点 | 到達性の前提にしてはいけない（A-2） | 拠点のワープがないと取れないかけらがある |

さらに **開発の順番** が加わる。
「計画では正しくつながっているが、まだ作っていないエリア B のせいで、作ったエリア C に今は行けない」
という状態は、開発中は正常だが、公開する区切りでは異常になる。
設計の誤り（赤）と、開発待ち（黄）を見分けられないと、どちらも見落とす。

## 2. 基本の考え方

### 2.1 世界は「状態のグラフ」

プレイヤーの状態を **（いる場所, mood, 装備しているエフェクト, 立てたフラグ, 取ったかけら）** とみなし、
動作や移動をその間の辺とする。到達性の問題は「始点から、この状態に行けるか」「この状態から、ベッドへ戻れるか」になる。

既存のゲーム理論から借りるもの：

| 理論 | 借りるもの |
|---|---|
| **鍵と扉**（ゼルダの迷宮の分析。Mark Brown の依存図が有名） | かけら・扉・エフェクトを「鍵」と「錠」の関係として図にする |
| **任務と空間**（Joris Dormans の Mission / Space グラフ） | 「何をする順番か」（任務のグラフ）と「どこにあるか」（空間のグラフ）を別の層として持ち、両方を重ねて見る |
| **ランダマイザーの論理と「球（sphere）」** | 「今の持ち物で取れる物を全部取る」を繰り返し、何周目で取れるかを番号にする。進行の深さとペースの物差しになる |
| **ペトリネット**（Machinations も同系統） | かけら・素材・重さを「トークン」として流し、量が足りるかを判定する |
| **強連結成分（SCC）・橋・関節点** | 戻れない場所、1 本切れると全部止まる通路を見つける |

### 2.2 単調な物と、行ったり来たりする物を分ける

探索が爆発しないように、状態を 2 種類に分ける。

| 単調（一度得たら失わない） | 行ったり来たり（場所と一緒に探索する） |
|---|---|
| 取ったかけら、立てたフラグ（決定 73 で消えない）、訪れたエリア | 場所、mood（20 通り）、装備（ベッドで付け替え）、切り替え（`toggle`。`scope: "area"` はそのエリアにいる間だけ、`world` は常に） |

- エフェクトは **取り消せる**（決定 28）ので「解放済み」は単調ではない。代わりに「**取ったかけらの合計で同時に装備できる組**」を、ベッドを通るたびに選び直せる、と扱う
- 条件に `not`（「風船を持っていないときだけ開く」など）がない限り、**同時に装備できる組のうち極大のものだけ**を調べればよい（条件が単調なら、多く持っているほうが必ず有利なので）。`not` を使った条件は正規化のときに印を付け、その分だけ組を増やして調べる

## 3. 構成（3 案と推奨）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | すべて MindBloom（Processing / Java）の中で解析する | 編集してすぐ結果が出る | ゲームの条件の意味（`src/plugins/conditions/`）を Java で二重に書くことになり、いずれずれる |
| B | ゲームのリポジトリの中に Web の開発用ページとして作り直す | スキーマ（zod）と条件をそのまま使える | MindBloom の 7,400 行（10 種の配置・レンズ・タイムマシン・分析画面）を捨てる |
| **C（推奨）** | **解析の本体はゲーム側の TypeScript**（`tools/atlas/`）。MindBloom は **表示・計画の編集・管理** を担当する | 条件の意味は 1 か所だけ。MindBloom の見せ方をそのまま使える | ファイルを介した受け渡しの仕組みが要る |

```
 content/（実データ）──┐
                        ├─▶ tools/atlas（TypeScript）──▶ planning/out/atlas.json ──▶ MindBloom（表示・シミュレーション）
 planning/world_plan.json┘     ・グラフを組む                 ノード・辺・正規化した条件         │
        ▲                      ・検査プラグインを全部走らせる  ・検査の結果（気づき）              │
        └──────────────────── 計画ノード・作業・マイルストーンを書き戻す ◀────────────────────┘
```

- MindBloom で計画を保存すると `npm run atlas` が走り（または `atlas -- --watch` が変更を拾い）、`atlas.json` が更新されたら MindBloom が位置を保ったまま読み直す（既存の `loadPreserve` を流用）
- **条件の正規化**：ゲームの条件プラグインに、ゲーム中の判定 `evaluate()` と並べて **`normalize()`** を持たせる。条件を「原子」（`effect:fish`、`mood:red`、`mood:*×moon`、`flag:x`、`frags>=6`、`weight>=20` など）の論理和・論理積（DNF）に直したものを `atlas.json` に書く。MindBloom は DNF を原子の集合で評価するだけなので、意味がずれない
  - 静的に評価できない条件（時刻・乱数など）は「不明」とし、両方の可能性を調べて警告する
  - 条件プラグインは段階 4 でまだ作っていないので、**作るときから `normalize()` を持つ形にする**のが一番安い
- 既に計画されている `tools/reachability.ts` は、この解析を呼んで赤の検査結果があれば失敗する薄い入口にする（CLAUDE.md の「エリアを足すときの手順」7 はそのまま）
- 地図帳は **開発専用**。`planning/` も MindBloom も公開版には含めない（「未訪問エリアの情報は出さない」と衝突しない）

## 4. ノードと辺

### 4.1 二つの層：包含の木と、つながりの辺

MindBloom の「親子の木＋手動リンク」という構造に、そのまま当てはめる。

- **包含の木**（親子）：世界 › エリア › 区画 › かけら・出入口・仕掛け。マインドマップとして眺める構造
- **つながりの辺**（リンクを拡張）：向き・種類・条件を持つ。到達性の解析はこちらだけを使う

### 4.2 ノードの種類（1 種類 1 ファイルのプラグイン）

ゲームの「拡張は 1 種類 1 ファイル」に合わせ、`tools/atlas/nodes/<kind>.ts` に **content から抽出する規則** と **完了の定義** を書く。

| 種類 | 元のデータ | 例 |
|---|---|---|
| `area` | `content/areas/<id>/area.json` ＋ `map.json` の `pos` | 沈んだ遊歩道 |
| `region` | `area.json` の `regions`（決定 71。省略時はエリア全体が 1 区画） | 水族館の天井側 |
| `fragment` | `fragments.json` | `aquarium_ceiling` |
| `effect` | `effect_tree.json`・`content/effects/` | 逆さ |
| `mood_source` | `events.json` の `setMood` などの動作 | 赤い光を浴びる場所 |
| `flag` | `setFlag` の動作と `{ "flag" }` の条件 | `sat_in_red_room` |
| `base` | `content/bases/` | 拠点 0（ベッドの部屋） |
| `resource` | 揺らぎ区域の素材・`gather` | 重りになる素材の産地 |
| `achievement` | `content/achievements/` | 日記のページ |
| `task` | 計画だけにある作業（原画の依頼など） | 「水族館の背景を描く」 |
| `milestone` | 計画だけにある区切り | 「試遊版 0.1」 |

### 4.3 辺の種類

| 種類 | 向き | 出どころ | 条件 |
|---|---|---|---|
| `adjacent`（端で隣り合う） | 両方向（※横視点は重力で片方向になりうる） | `map.json` の位置から自動。**境界に通れるタイルがあるか**も数える | 区画ごとの条件 |
| `warp` | 片方向／両方向 | `map.json` の `warps` | ワープの `requires` |
| `exit` | 片方向 | `area.json` の `exits` | 出入口の `requires`、沈みの重さ |
| `requires`（要求） | 錠 → 鍵 | かけら・扉の `requires` | — |
| `prereq`（前提） | エフェクト → エフェクト | `effect_tree.json` | かけらの数 |
| `produces`（作る） | 場所 → mood / フラグ | `events.json` | きっかけの条件 |
| `build`（作る順） | 作業 → 作業 | 計画だけ | — |

### 4.4 計画ノードと実データノード（ID の予約）

- MindBloom で作った計画のノードは、**ゲームの ID をその場で決めて予約**する（`planned: true`）。ID は変えない・消さない、の規則にそのまま乗る
- `tools/new-area.ts` などで同じ ID の実データができると、そのノードは自動で「実装済み」に変わる
- 実データ由来のノードは MindBloom では **鍵の印を付けて編集不可**（直すのは content 側）。計画ノードだけ自由に編集できる
- 計画に書いた条件と、実装された条件が違うときは「設計のずれ」として知らせる

## 5. 検査の段階

検査は `tools/atlas/checks/<name>.ts` に 1 種類 1 ファイルで足す。どれも
`{ 重さ: 赤 / 黄 / 情報, ノード, 文, 直し方の候補 }` を返し、MindBloom の「気づき」（クリックで対象へ飛ぶ・対応する）にそのまま並ぶ。

### L0 構造（条件を見ない）

| 検査 | 内容 |
|---|---|
| **孤立** | どの辺ともつながっていないノード。MindBloom では画面の端の「虚無」に漂わせる（ゲームの虚無と種の考え方に合わせた見せ方） |
| 参照切れ | 存在しない ID を指す出入口・ワープ・条件 |
| 重複 | 同じ ID |

### L1 位相（条件を無視して、つながりだけ）

| 検査 | 内容 |
|---|---|
| **到達不能（位相）** | 始点からどの道をたどっても行けない |
| **帰還不能（位相）** | 行けるが、そこから起点（ベッド）へ戻る道がない。SCC で、起点を含む成分に戻れない成分を探す |
| 閉じた境界 | 地図では隣り合うのに、境界に通れるタイルが 1 つもない |
| 危ない境界 | 視点・重力の違う境界（C-4）、横視点で通れるタイルが空中にしかない境界 |

### L2 論理（条件を評価する）

「球」の解析（2.1）：

```
持ち物 = { かけら: なし, フラグ: なし }
球 = 0
繰り返す:
  装備の候補 = 取ったかけらで同時に解放できるエフェクトの組（前提を満たし、極大のものだけ。not があれば追加）
  装備の候補それぞれについて:
    （場所, mood）を（ベッド, 白×風）から探索する。辺の条件は 装備・mood・フラグ・かけらの数 で評価
    フラグは行けた所で立てる
    かけらは「拾った後、同じ装備のままベッドへ戻れる」所のものだけ拾える
      （エフェクトの木で使うにも、揺れるかけらを確定するにも戻る必要があるため）
  新しく拾えた物がなければ終わる
  拾えた物に番号「球」を付けて持ち物に足す。球 += 1
最後まで拾えなかったかけら・行けなかった区画 = 到達不能
```

| 検査 | 内容 |
|---|---|
| **到達不能（論理）** | 上の解析で最後まで取れないかけら・開かない扉・行けない区画 |
| **理由の説明** | 届かない物ごとに「足りない原子」の最小の組を出す。例：`aquarium_deep_1 に届かない：effect:fish（解放に 6 必要、届くかけらの合計は 5）` |
| **詰み（帰還不能・論理）** | ある装備・mood で行けるのに、そこからベッドへ戻れない状態。例：逆さで入ると出口が天井側にしかなく、天井へ上がる手段が逆さ以外にない |
| 循環 | 鍵が自分の錠の向こう側にしかない（理由の説明で循環として表示） |
| 封じたエフェクト | `effectPolicy` で封じたエフェクトを前提にした物（C-11） |
| mood の欠け | 条件に出てくる mood を作る場所がない、または作れる場所から目的地まで保てない |
| フラグの欠け | 読むだけで立てる場所がない（赤）／立てるだけで誰も読まない（情報） |
| 拠点なしの保証 | 拠点の mood 固定・拠点間ワープを外して解析しても全部取れるか（A-2 の不変のルール） |

### L3 資源（量が足りるか）

| 検査 | 内容 |
|---|---|
| 沈み | `weight>=N` を「その時点で行ける、より浅いエリアの素材で重さ N を集められる」と読み替えて評価 |
| かけらの経済 | 全部のかけらを取るのに要る最小の装備のコストと、取れるかけらの合計の差（**余裕**）。0 なら全部探し尽くさないと進めない |
| 揺らぎ区域 | 生成器が保証すると申告した道だけを使う |

### 目覚めと検査の重さ（決定 70）

どこからでも目覚めてベッドに戻れるので、「戻れない」の重さは深さで変わる。

| 状態 | 重さ |
|---|---|
| 深さ1〜3の行き止まり（歩いて戻る道がない） | 情報（「目覚めないと戻れない」と表示） |
| 深さ4以上の行き止まり | 黄（戻るには素材を失う） |
| 揺れるかけらを取った後、目覚めずに拠点へ戻る道がない | **赤**（そのかけらは実質、確定できない） |

L2 の解析では、深さ1〜3の場所からベッドへ向かう「目覚め」の辺を足す。深さ4以上からの目覚めの辺は、揺れるかけらを持っていない状態にだけ足す。

### 開発の状態との重ね合わせ（赤・黄・緑）

解析を **2 回** 走らせる。「計画の世界」（計画ノードも含む）と「今の世界」（実装済みだけ）。

| 計画の世界 | 今の世界 | 色 | 意味 |
|---|---|---|---|
| 届く | 届く | 緑 | 問題なし |
| 届く | 届かない | **黄** | 開発待ち。足を引っ張っている未実装のノードを表示する |
| 届かない | — | **赤** | 設計の誤り。今すぐ直す |
| 届く | 戻れない | **紫** | 今の世界だけの詰み。公開の区切りの前に必ず消す |

## 6. 統計と指標

数値は分析画面（MindBloom の I）に出す。基準値はすべて仮で、遊んでから調整する。

| 指標 | 求め方 | 分かること |
|---|---|---|
| 球の数・球ごとのかけら数 | L2 の解析 | 進行の長さとペース。途中で 0 や 1 が続く所は退屈な区間 |
| **選択肢の幅** | 各球で、同時に取りに行けるかけら・エリアの数 | 1 が続けば一本道、多すぎれば迷う。メトロイドヴァニアらしさの物差し |
| 鍵の働き | エフェクトごとに、それが条件に出てくる辺の数・開くかけらの数 | 0 は使われない鍵。1 つしか開かない鍵は弱い。**複数のエリアで使われる鍵**ほど「戻ってくる楽しさ」を作る |
| 戻り道の長さ | 新しく開いた場所まで、ベッドから何回エリアを移るか | 往復の負担。長すぎる所には近道を計画する |
| 深さと球の相関 | 深さ（1〜7）と、そのエリアに初めて行ける球の順位相関 | 深いエリアが後半に来ているか（難しさの曲線） |
| 橋・関節点 | Tarjan の方法 | そのエリアや通路が 1 つ欠けると後ろが全部止まる単一障害点。開発ではそこが遅れると全体が止まる |
| 媒介中心性 | 最短路が何本通るか | 混雑するハブ。ベッドの部屋が高いのは正常、それ以外が高すぎると渋滞 |
| mood の網羅 | 20 通りのうち、作れる・条件に使われる数 | 使われていない mood、作れない mood |
| 状態の倍率 | 20（mood）× `scope: "world"` の切り替えの値の数の積 | 解析の重さ。一定を超えたら警告（切り替えを mood で表せないか見直す） |
| 迷子度 | 状態グラフの上でランダムに歩く模擬プレイヤーを多数走らせ、各かけらに着くまでの歩数の分布（モンテカルロ法） | 隠しすぎ・遠すぎのかけら。分散が大きい所は人によって詰まる |
| 余裕（L3） | — | かけらの探し尽くしを強いていないか |

## 7. 開発のマネジメント

### 7.1 進み具合は「申告」ではなく「事実」から計算する

ノードの種類ごとに **完了の定義** をチェック項目として持ち、リポジトリの事実から自動で判定する。
MindBloom の進捗（％）とその集計（親への積み上げ）は、手入力ではなくこれで埋まる。

例：エリアの完了の定義（CLAUDE.md の「エリアを足すときの手順」から）

| 項目 | 判定 |
|---|---|
| 世界観のメモ | `notes.md` がある |
| データ | `area.json`・`tiles.json` がスキーマを通る |
| 配置 | `map.json` にあり、L1 で起点とつながる |
| 素材 | 使う物に `provisional: true` がない／仮のアセットがない |
| 日記 | このエリアの実績が 1〜3 枚ある |
| かけら | エフェクトの木との釣り合い（L3 の余裕）を確認済み |
| 検査 | 赤・紫の検査結果がない |
| 歩いて確認 | **手動のチェック**（MindBloom で印を付けると `world_plan.json` に記録） |

### 7.2 区切りは「遊べる世界」として定義する

- マイルストーンは「この時点で実装済みのノードの集合」。その集合だけで解析して **赤・紫が 0、黄は区切りの外にだけある** ことを、区切りの合格条件にする（いつでも遊べる状態を保つ）
- 区切りごとに、球の数・かけら数・選択肢の幅を記録し、世界が育つ様子をタイムマシン（MindBloom の R）で再生する

### 7.3 作る順番の提案

- 計画の世界の **球の順** が、そのまま作る順の下書きになる（前の球のエリアがないと、後の球は試せない）
- 作業に見積もり（日数）を付ければ、`build` の辺と合わせて **臨界経路**（一番長い依存の鎖）を出せる
- 橋・関節点にあたるエリアは、遅れると後ろが全部「黄」のまま止まるので先に作るか、迂回路を計画する

### 7.4 そのほか

- 停滞：長く更新されていない計画ノード（MindBloom の「鮮度」レンズを流用）
- 原画の依頼（`docs/art_requests.md`）と仮の当たり判定（`provisional`）の残数を作業として数える
- カンバンの列ごとに同時に進める数の上限（WIP）を決められるようにする

### 13.2 ゲーム側：解析の動かし方

**Content をそのまま使う。** 検証の中身をゲームと同じにするため、解析は `src/engine/content.ts` の `Content` で content を読む。
ただし `Content` は Vite の `import.meta.glob` で読み込むので、素の `node` では動かない（`tools/import-art.ts` は fs で読んでいる）。そこで：

- `tools/atlas/index.ts` は Vite（すでに入っている）をプログラムから起動し、そのモジュールランナー（`ssrLoadModule` 相当）で `tools/atlas/build.ts` を読み込む。これで `import.meta.glob` もプラグインの自動登録も、ゲームと同じに動く。**依存パッケージは増えない**（Vite 8 での正確な API は実装のときに確かめる）
- PNG の読み込み（テストの `decodePngFile`）と、プレイヤーを歩かせる部分（テストの `Walker`）は、`tests/content.test.ts` から `tools/lib/` に移してテストと解析で共有する
- `--watch` では Vite の監視をそのまま使い、`content/` が変わったら作り直す

```
npm run atlas                 # 1 回解析して planning/out/atlas.json を書く。赤があれば終了コード 1
npm run atlas -- --watch      # content/ の変更を監視して書き直し続ける
npm run atlas -- --quiet      # 要約を出さない（MindBloom から動かすとき）
```

- `tools/reachability.ts` は `atlas` を呼んで終了コードを返すだけの入口にする（CLAUDE.md の手順 7）
- 出力：`planning/out/atlas.json`、`planning/out/mosaic/<area>.png`（13.8）。`planning/out/` は `.gitignore` に足す
- 書き出しは一時ファイルに書いてから名前を変える（MindBloom が書きかけを読まないように）

### 13.3 グラフの組み立て

**起点** は `map.json` の `start.area`（ベッドの部屋）。目覚めた先もここ（決定 70）。

| ノード | ID | 親 | 持つ値 |
|---|---|---|---|
| 世界 | `world` | — | 地図の範囲 |
| エリア | `area:<id>` | `world` | 名前・深さ・視点・大きさ・位置・ループ・重力・揺らぎ区域か・拠点にできるか |
| 拠点 | `base:<area>` | そのエリア | 最初からの拠点か・段階の数 |

| 辺 | ID | 向き | 出どころ |
|---|---|---|---|
| 境界の口 | `adj:<a>><b>#<n>`（n は口の番号。境界に沿って順に） | 試験で通れた向きだけ | 13.4 |
| 出入口 | `exit:<area>/<exitId>` | 片方向 | `area.json` の `exits` |

| 目覚め | `wake:<area>` | 片方向（→ 起点） | 決定 70。図には既定で描かない。「戻る」の計算には使わず、区別のためだけに持つ |

ID は content の ID から機械的に作るので、content の ID を変えない限り変わらない。MindBloom はこの ID でノードの位置を覚える。

### 13.4 境界の口と通過試験

**口を探す。** 地図で辺が接している 2 つのエリアについて、接している辺に沿って 1 マスずつ、両側のマス（境界のすぐ内側）が通れるかを見る。当たり判定は置いた物も含めた `LoadedArea.solid` を使う。通れるマスが続く区間を 1 つの「口」とする。

- 横視点で横向きに越える口は、高さ 2 マス以上ないとプレイヤー（当たり判定 10×20）が通れない。1 マスだけの口は「狭すぎる口」として情報に出す
- **ループする端に隣のエリアが接している** 場合、ゲームはループを優先するので（`makeSolidQuery`・`checkEdge`）、その境界は通れない。口があっても辺にせず、検査で知らせる

**向きごとに物理で試す。** 口ごとに、両方の向きについて：

1. 出る側のエリアで、口の近く（口の中で重力の向きに一番「下」のマスから 2 マス内側を中心に、4 マス以内）の足場にプレイヤーを立たせる。横視点は足場の上、見下ろしは壁に埋まらない所。見つからなければその位置の空中から始める（下へ落ちて越える口のため）
   - ゲームの `findSafeSpot` は使わない。隣のエリアの足場まで探すので、口の向こう側に立ってしまい、登れない口でも「越えた」ことになる（実装中に見つかった）
2. 口の向こう側の点へ向かって入力を決めながら最大 4 秒（240 ステップ）動かし、`checkEdge` で行き先のエリアに入ったら成功
3. だめなら、足場にいるたびにジャンプを押しながらもう一度試す
4. 着いた側の安全は、出現位置などと同じ `unsafe_landing` の検査に任せる

| 結果 | 辺 | 図での見た目 |
|---|---|---|
| 歩いて越えた | 作る（`pass: "walk"`） | 実線 |
| 跳んで越えた | 作る（`pass: "jump"`） | 実線＋小さな弧の印 |
| 越えられなかった | 作らない | 口の位置に × |

- 試験は「越えられる」ことの証明にはなるが、「越えられない」ことの証明にはならない（離れた所から助走すれば跳べる、など）。越えられなかった向きは情報として出し、通れるはずなら試験の始め方を見直す
- 見下ろしのエリアどうしは、口があれば必ず歩いて越えられるが、同じ仕組みで試す（例外を作らない）
- 試験はエリアの数 × 口の数 × 2 回で、4 エリアなら一瞬。100 エリアでも数秒の見込み

### 13.6 到達の計算

- **行ける**：起点から、辺（口・出入口・ワープ）を前向きにたどった幅優先探索
- **戻れる**：起点へ向かって、辺を逆向きにたどった幅優先探索（目覚めの辺は使わない）
- 結果を、エリアごとに次のどれかにする（MindBloom のレンズの色になる）

| 状態 | 条件 | 色 | 記号 |
|---|---|---|---|
| 起点 | `start.area` | アクセント色 | ◎ |
| 行き来できる | 行ける・戻れる | 緑 | ● |
| 目覚めで戻る | 行ける・戻れない・深さ1〜3 | 青 | ◇ |
| 失って戻る | 行ける・戻れない・深さ4以上 | 琥珀 | ▲ |
| 行けない | 行けない | 赤 | × |
| 孤立 | 辺が 1 本もない | 灰 | ○ |
| 消えた（MindBloom だけ） | 前の解析にはあったが、今の content にない | 濃い灰 | ？ |

色だけに頼らないよう、記号を必ず添える（ゲームの mood の印と同じ考え方、C-2）。記号は MindBloom のフォントにある JIS の記号だけを使う（↺・⚠ は表示できなかった）。

統計（P0 で出すもの）：エリア数、種類ごとの辺の数、行き来できるエリアの割合、一方通行の数、**関節点**（そのエリアがなくなると世界が分かれる）と **橋**（その辺がなくなると世界が分かれる）。どちらも向きを無視した図で求める。

### 13.7 `atlas.json`（P0 の形）

今の世界で書き出したもの（一部）：

```jsonc
{
```

### 13.8 MindBloom 側

**地図帳は専用の文書として開く。** ふだんのマインドマップ（価値観マップなど）とは混ぜない。

- 開き方：起動の引数 `--atlas`、またはコマンドパレットの「地図帳を開く」
- 表示の状態（位置・折り畳み・配置・レンズ・自分で足したメモ）は `MindBloom/data/atlas_view.json` に自動保存（ふだんの `autosave.json` とは別。決定 74）
- 設定は `MindBloom/data/atlas_config.json`：`{ "gameRepo": "C:\\勉強\\2_little_world_app", "runAnalyzer": true }`

**データモデルの拡張**（`Model.pde`）

| クラス | 足すもの |
|---|---|
| `Node` | `kind`（world / area / base / note …）、`gid`（atlas の ID）、`origin`（`content` / `note`）、`attrs`（JSONObject。モザイクのパスもここ）、`reach`。編集できるかは `isContent()` で決める |
| `Link` | `kind`（adjacent / exit / warp / wake / manual / wiki）と `data`（atlas.json の辺そのもの） |
| `MapModel` | `atlasEdges`（atlas.json の辺。ノードは gid で引くので、Undo で作り直されても切れない） |
| 保存形式 | `format: 2`。`format: 1` の文書は、全ノードを `kind: "note"`・`origin: "note"` として読む。地図帳の文書には、最後に読んだ解析の結果（`atlasCache`）も保存し、解析が動いていなくても検査結果を見られる |

- content 由来のノード（`origin: "content"`）は **鍵の印付きで編集できない**（題名・親子・削除）。直すのは content 側
- 自分で足したノードは `origin: "note"`。content 由来のノードの子にメモを付けられる（「ここの背景は夕焼けにしたい」など）。計画ノードではないので、ゲームの ID は持たない（計画ノードは P1）

**取り込み**（新しく `Atlas.pde`）

- `planning/out/atlas.json` の更新時刻を 1 秒ごとに見て、変わったら読み直す
- `gid` で突き合わせる：ある → 値を更新（位置はそのまま）、新しい → 親の近くに出現、**消えた → 灰色の「消えた」ノードとして残し、気づきに出す**（ID は消さない規則なので、消えたら誤りの可能性が高い）
- 自分で足したメモはそのまま残る
- 画面の上に解析の状態と赤・黄・情報の数を出す：「解析：最新 10:52:29　赤 0・黄 0・情報 1」「解析を起動しました」「失敗（理由）」「atlas.json がない」

**解析を誰が動かすか**（決定 75）：MindBloom が地図帳を開いたときに `node tools/atlas/index.ts --watch --quiet` を子プロセスとして起動し、閉じるとき（ふだんの文書に戻るとき・終わるとき）に子孫のプロセスごと止める。`exit()` を通らずに終わったときのために、JVM の終了時にも止める。

起動の引数（確かめるとき用）：`--atlas-repo=<フォルダ>` で設定のリポジトリを一時的に差し替える。`--atlas --selftest=<出力>` は解析を起動せず今ある `atlas.json` だけで撮る。`--atlas-live` を足すと解析の起動・停止も確かめる。

**地図の配置**（新しい配置 `L_MAP`）

- エリアのノードを、`map.json` の位置どおり（エリアの中心 × 1 マスあたり 8px）に置く
- ノードの下に **エリアの四角** を描く（既存のカンバンやマトリクスの背景を描く仕組みと同じ）。中には解析が書き出したモザイク（`mosaic/<area>.png`。ゲームの地図と同じ `buildMosaic` で作る）を薄く描き、深いエリアほど暗くする（03 深さ）
- 境界の口を、四角の辺の上の太い線で描く。両方の向きに越えられる口はミント、片方だけは金で越えられる向きに矢印、どちらも越えられない口は珊瑚色に ×。歩いたか跳んだかは、まだ見た目で区別していない
- ワープは流れる点線の曲線で、出入口は実線で、それぞれ実際の位置どうしを結ぶ（向きごとに矢印。両方向のワープは 2 本の弧になる）
- 拠点は、エリアの四角の右上に小さなノードとして置く
- エリアの四角は少し透ける塗りで描くので、重なっても下が見える（重なったエリアを切り替えて見せる仕組みは、重なったエリアができてから）
- 地図に置かれていないエリアは、地図の下に並べる。自分のメモは親の右に積む
- 配置の帯の先頭に「地図」を足す（地図帳の文書でだけ出す。キーは Shift+M）。既存の 10 個の配置（1〜0 キー）は変えない

**到達性のレンズ**

- 既存のレンズは 0〜1 の連続した値を色の帯にしているが、到達性は種類なので、`targetColor()` に「種類の色」の分岐を足す（13.6 の表の色と記号）
- 記号はノードの左上に小さく描く。content 由来のノードの右上には鍵の印。到達性のレンズはふだんの文書では選べない

**気づき**

- `findings` を既存の「気づき」（`Insight`）に並べる。赤 → 黄 → 情報の順で、最初の直し方の候補を「→」で添える。クリックすると対象のノードを選んでカメラが飛ぶ。地図帳では、ふだんのマインドマップ向けの気づき（期限切れなど）は出さない
- 力学の配置（有機グラフ）で孤立したノードを外周の「虚無の輪」に押し出す見せ方は、**まだ作っていない**（P1 で）

**分析画面**（I）は地図帳用に差し替える：エリア数・行き来できる割合・赤・黄のカード、到達の内訳、単一障害点（関節点・橋）、検査の結果。
